# アーキテクチャ解説

本ドキュメントでは、Simeji Windowsのシステム設計、コンポーネント構成、各クレートの責務、および主要な設計判断の背景について解説します。製品要件については[製品仕様書](specification.md)、検証実績については[検証状況と残課題](status.md)を参照してください。

## 1. システム全体図

本システムは、入力対象アプリケーション内に読み込まれる軽量なTSF対応DLLと、ユーザーセッションごとに常駐して重厚な変換エンジンを安全に保持するバックグラウンドワーカーによる、**2プロセス構成**を採用しています。

```text
入力対象アプリケーション（任意のプロセス / AppContainer含む）
  └─ TSFインプロセスDLL（crates/ime: simeji_ime.dll）
       │
       │  名前付きパイプ通信（crates/transport, crates/protocol）
       ▼
  変換ワーカープロセス（crates/worker: simeji-worker.exe）
       ├─ プライマリ変換エンジン（crates/engine: 文節変換・確定・学習）
       ├─ セカンダリ変換エンジン（予測候補キュー: 非ブロッキング事前変換）
       ├─ ユーザー辞書・学習データマネージャー
       └─ クラウド通信キュー（Simeji超変換API・キャッシュ）
```

## 2. クレート構成と責務

Cargoワークスペースは、プロセス境界および関心事の分離に基づいて以下の5つのクレートに分割されています。

| クレート名 | 種別 | 主な成果物 | 責務 |
| --- | --- | --- | --- |
| `crates/ime` (`simeji-ime`) | cdylib / bin | `simeji_ime.dll`<br>`simeji-setup.exe` | TSFテキストサービス、候補ウィンドウ描画、UIオートメーション、システム登録ツール |
| `crates/worker` (`simeji-worker`) | bin / lib | `simeji-worker.exe`<br>`simeji-launcher.exe`<br>`simeji-cloud.exe` | 変換常駐ワーカー、起動ランチャー、クラウド変換設定CLI、予測候補キュー |
| `crates/engine` (`simeji-engine`) | rlib | ライブラリ | Unicornエミュレーターを用いたARM版Simejiエンジンの実行、Linux ABIエミュレーション |
| `crates/protocol` (`simeji-protocol`) | rlib | ライブラリ | DLLとワーカー間で送受信されるメッセージ型（要求・応答）の定義 |
| `crates/transport` (`simeji-transport`) | rlib | ライブラリ | セキュアな名前付きパイプ通信基盤（AppContainer対応ACL、タイムアウト制御） |

## 3. TSF連携層（`crates/ime`）の設計

`crates/ime` は、WindowsのText Services Framework（TSF）およびCOMインターフェースを実装するインプロセスDLLです。ホストプロセスの安定性を確保するため、変換エンジン本体は保持せず、入力ロジックを**「TSF非依存層」**と**「Windows/TSF連携層」**の2層に厳密に分離しています。

### 3.1 TSF非依存層（入力ロジック）
実機環境やTSFの複雑なCOMコンテキストに依存せず、単体テストを高速かつ決定論的に実行できるよう設計されています。

- **`keys`**: 仮想キーコード（VKコード）および修飾キーの状態を、IMEの抽象操作（変換、確定、取り消し、文節移動、候補選択など）へマッピングします。タッチキーボード特有のキー（`VK_PACKET` による候補ページ送りコード等）もここで識別します。
- **`composer`**: 未確定文字列の合成状態を管理するステートマシンです。入力中のカーソル位置、ローマ字・ひらがな変換、文節ごとの読み・表記、選択候補を追跡し、キー入力に応じてエディタに反映すべき操作群を生成します。確定時には選択された文節の文脈関係を学習データとして記録します。
- **`candidates`**: ローカル変換エンジンから取得した候補と、非同期で取得されたクラウド候補を統合し、ページ単位（最大9件）で管理します。
- **`worker`**: 変換ワーカーへのIPCクライアントです。`composer` はこのトレイトを通じて変換要求を行います。

### 3.2 Windows / TSF連携層
TSFおよびWin32サブシステムとのブリッジを担当します。

- **`dll`**: COMインプロセスサーバーのエントリポイント（`DllGetClassObject`, `DllCanUnloadNow` 等）を実装します。
- **`text_service`**: `ITfTextInputProcessorEx`, `ITfKeyEventSink`, `ITfCompartmentEventSink` などを実装するコアクラスです。キーイベントを `composer` へ渡し、返された操作をTSF編集セッション（`edit_session`）を通じてドキュメントバッファへ反映します。
- **`input_mode` / `mode_icon`**: 日本語入力のオン／オフ（オープン／クローズ）状態をTSFコンパートメント（`GUID_COMPARTMENT_KEYBOARD_OPENCLOSE`）で集中管理します。タスクバーの入力インジケーターには、実行時にDirect2Dで動的描画した鮮明な「あ」「A」アイコン（メイリオ準拠）を登録・表示します。
- **`candidate_window`**: 変換候補および予測候補を表示する独自のポップアップウィンドウです。Direct2DおよびDirectWriteを用いたハードウェアアクセラレーション描画により、カラー絵文字、滑らかな角丸、モダンなアイコン表示を実現しています。
  - **インプレース更新**: 入力中のキー打鍵ごとにウィンドウの破棄・再生成を行わず、位置・サイズ・表示内容に変化があった場合のみ画面外バッファ（ダブルバッファリング）経由で更新することで、画面のちらつきを完全に防止しています。
  - **DPI自動追従**: 所有元ウィンドウのDPIスケーリングに自動適応し、マルチモニター環境や高DPI環境でも最適なサイズで描画されます。
  - **画面外はみ出し防止**: モニターの作業領域やタッチキーボード（`IFrameworkInputPane`）との衝突を検知し、未確定文字列の下側または上側へインテリジェントに配置します。
- **`candidate_accessibility`**: UI Automation（UIA）規格に準拠したアクセシビリティプロバイダーです。候補リスト（`IME_Candidate_Window`）および各項目の選択状態・クラウド属性をスクリーンリーダー等の支援技術へ通知します。
- **`candidate_element`**: TSFのUI要素マネジメント（`ITfCandidateListUIElementBehavior`, `ITfIntegratableCandidateListUIElement`）を実装し、全画面ゲーム等のUIレスモードを要求するアプリケーションへ候補情報を提供します。
- **`functions`**: TSFの関数プロバイダー（`ITfFnSearchCandidateProvider`）を実装し、Windowsの統合検索におけるサジェスト機能や、タッチキーボードへの最適化レイアウト（`TKBL_OPT_JAPANESE_ABC`）の通知を担います。
- **`lookup_timer`**: 未確定入力中の予測候補照会結果を、バックグラウンドワーカーからポーリング（40ms間隔）で取得し、キー入力処理を一切ブロックすることなく候補ウィンドウを更新します。

## 4. 変換ワーカー（`crates/worker`）の設計

`simeji-worker` は、ユーザーのログインセッションごとに1つ動作する常駐プロセスです。

### 4.1 プロセスモデルと常駐性
ホストアプリケーション（Webブラウザ、Office、エディタ等）のクラッシュや予期せぬ終了から変換状態を保護するため、変換処理を別プロセスとして隔離しています。
通常権限で動作し、サインイン時に `simeji-launcher.exe` を通じて多重起動を防止しつつ自動起動されます。

### 4.2 非ブロッキング予測候補キュー（`SuggestionQueue`）
文節変換エンジンは呼び出しの並行処理に対応しておらず、長い文の変換には数十〜数百ミリ秒を要する場合があります。これを単一のエンジンで直列処理すると、タイピング中に次のキーのローマ字変換が待たされる原因となります。
この遅延を排除するため、ワーカー内では**予測候補専用のセカンダリエンジン**を別スレッドで待機させています。
- 最新の読み仮名のみをバックグラウンドで処理し、古い要求は自動的に破棄されます。
- 一定時間（5分間）入力がない場合はセカンダリエンジンを自動解放し、メモリリソースを節約します。

### 4.3 クラウド変換連携（`CloudQueue` / `CloudClient`）
クラウド超変換APIへのHTTPリクエストを非同期キューで管理します。
- 読み仮名が更新された場合、古いリクエストの応答は自動的に破棄されます。
- 受信したクラウド候補は、既存のローカル候補の末尾に追記され、すでにユーザーがフォーカスしている選択位置を崩さないよう制御されます。

## 5. 変換エンジンラッパー（`crates/engine`）

`crates/engine` は、Android版Simejiのネイティブ共有ライブラリ（`libbaiduime.so`, `libbaiducmph.so`）をWindows x64上で透過的に実行するための変換コアです。

### 5.1 ARMエミュレーションとLinux ABI補完
- **CPUエミュレーション**: Unicorn Engineを活用し、ARMv7コードをメモリ上で直接エミュレート実行します。
- **ELFローダー**: Android向けの共有ライブラリ（ELF形式）をメモリに展開し、シンボル再配置とリンクを動的に行います。
- **Linux / Android libc互換レイヤー（`host`モジュール）**: ネイティブライブラリが要求するメモリ管理（`malloc`/`free`）、文字列操作、ファイルI/O、スレッド同期、時刻取得などのシステムコールを、Rustによるホスト側実装へルーティングします。

### 5.2 タイムアウト監視機構（`watchdog`）
Unicorn組み込みのタイムアウト機構は、呼び出しごとに専用スレッドを生成・破棄するためオーバーヘッドが大きく、タイマー分解能に起因する待機遅延が発生していました。
本システムでは独立した軽量なWatchdog監視スレッドを常駐させ、規定時間を超過した処理のみを外部から安全に停止させる方式へ刷新し、関数呼び出しのオーバーヘッドを大幅に削減しています。

## 6. プロセス間通信（IPC）とセキュリティ

通信基盤（`crates/transport`）には、Windowsの名前付きパイプを採用しています。

### 6.1 パイプエンドポイントの命名規則
パイプ名はユーザーのSIDおよびセッションIDに基づいて分離されています。
```text
\\.\pipe\SimejiWindows\<User-SID>\<Session-ID>\Worker
```

### 6.2 セキュリティ記述子とアクセス制御
Microsoft IMEの要件に準拠し、セキュリティが強化されたWindowsストアアプリ（UWP）や、Edge/Chromeなどのサンドボックス環境（AppContainer）、低整合性レベル（Low Integrity）のプロセスからの接続を可能にしています。
- パイプの所有者を実行ユーザーのSIDに固定。
- 同一ユーザーおよび同一ユーザーのAppContainer SIDに対して読み書き権限を明示的に付与。
- クライアント側は接続先パイプの所有者が自身と同一であることを検証し、安全性を担保します。

## 7. ファイル配置とライフサイクル管理

### 7.1 ディレクトリ構成

| 配置先 | 主な配置ファイル | アクセス権限 |
| --- | --- | --- |
| `%ProgramFiles%\SimejiWindows\` | `simeji_ime.dll`<br>`simeji-worker.exe`<br>`simeji-launcher.exe`<br>`simeji-cloud.exe`<br>`Dictionary\*`（辞書アセット） | 管理者書き込み / 全ユーザー・AppContainer読み取り可能 |
| `%LOCALAPPDATA%\SimejiWindows\` | `settings.json`（設定ファイル）<br>`user-dictionary.json`（ユーザー辞書）<br>`Learning\`（学習データ）<br>`Cache\`（キャッシュデータ） | 各ログインユーザー固有の読み書き |

### 7.2 アップデートおよびアンインストール設計
TSF DLLは、IMEを使用しているすべてのアプリケーションのメモリにロードされるため、実行中のファイル置換がOSによってロックされます。
`simeji-setup.exe` では、使用中のファイルを安全に退避名義に変更した上で、Windows標準の `MoveFileExW(..., MOVEFILE_DELAY_UNTIL_REBOOT)` を利用して次回のOS再起動時に確実に削除・更新されるよう設計されています。
